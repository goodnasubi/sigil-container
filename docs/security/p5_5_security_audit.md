## 隔離境界についての重要告知

> [!WARNING]
> **コンテナはカーネルを共有する。信頼できないコードの実行に対する完全な境界とは扱わず、その用途はマイクロ VM のバックエンド（後続）を前提にする。**
> 利用者向けのエラーメッセージおよび境界告知文（`isolation_boundary_notice()`）において、この前提を常に明示する。管理 HTTP API においては、情報漏洩やフィンガープリンティングを防ぐため、存在秘匿（404 `not found`）や最小限のエラー応答（401 `unauthorized` 等）を維持する。

### 監査項目 1: 秘密（Secrets）の取り扱い
- **環境変数での受け渡し禁止**: 秘密（HMAC 認証鍵、コンテナ秘密値）は環境変数ではなく、ファイル（メモリ上の `Secret` 型）で渡す仕様を遵守。
- **平文露出の排除確認**: 401 認証拒否応答（本文 `unauthorized` のみ、`WWW-Authenticate: Bearer`、`Cache-Control: no-store`）やエラー型において、鍵やトークンなどの秘密情報・内部パスを一切露出しないことを確認。
- **バックアップの秘密性**: バックアップアーカイブ（`BackupArchive`）は原本データと同一の機密レベルとして扱い、テストにおいては公開された固定の使い捨て鍵・データのみを使用。

### 監査項目 2: 上限（Resource Limits）の徹底
- **読み込み前適用**: すべての上限は意味解釈・デコード前に適用され、超過時に自動分割や黙った切り捨てを行わず、明示的なエラー型（`LimitExceeded` / HTTP 413 / HTTP 429 / HTTP 507）で即時拒否。
  - 仕様サイズ上限: 64 KiB (`max_spec_size`)
  - 管理 API トークン長上限: 1,024 byte (`max_admin_token_size`)
  - 管理 API ペイロード長上限: 404 byte (`max_admin_payload_size`)
  - 同時操作数上限: 16 (`max_concurrent_operations`、超過時は 429)
  - ログバッファ上限: 100 MiB (`max_log_size`、超過時は 507)
  - ワークロード数上限: 1,024 (`max_workload_count`)
  - レプリカ数上限: 64 (`max_replicas`)
  - 宣言コミット履歴保持上限: 256 (`max_declaration_commits`)
  - バックアップマニフェストサイズ上限: 64 KiB (`max_backup_manifest_size`)

### 監査項目 3: 信頼基盤（TCB）の最小化
- 純 Sigil（`targets server` / `trust none` / `effects none`）で実装され、アプリケーション側に `raw.*` や `unchecked` などの未検証脱出ハッチを追加していない。
- 外部クレートや未知のネイティブ C ライブラリへの依存なし。
- 依存する `sigil` コンパイラは README 記載の固定コミット SHA（現行 main）に基づく。

## 2. P5-5 完了条件の検証結果

### (1) 認証・認可の否定試験と要求検証
- **認証否定**: トークン欠落、不正スキーム、不正署名、有効期限切れ（`now >= exp`）、未来発行（`now < iat`）、audience 不一致、トークン長超過（1,024 byte 超）がいずれも固定 401（本文 `unauthorized`、`WWW-Authenticate: Bearer`、`Cache-Control: no-store`）で拒否されることを確認（`tests/test_admin_api.sigil`）。
- **認可否定と存在秘匿**: 権限のない主体からのアクセス要求に対し、リソースが存在する場合であっても 403 ではなく **404 Not Found**（`not found`）を返し、読めない対象の存在を外部に漏洩させないことを検証。
- **権限変更の即時反映**: `grant_permission` および `revoke_permission` による権限変更が、次のリクエストから直ちに評価結果に反映されることを検証。
- **管理 API 骨格と要求検証**: POST /api/v1/workloads による作成時の識別子厳格検証（空文字、`*`、`a/b` 等の拒否）および重複登録拒否（400）、多重スラッシュ経路の拒否（404）を確認。実体（調整ループ・ModelRuntime・DeclarationRepository）との統合は後続の結合段階で行う骨格設計とする。

### (2) 宣言の差分と原子的検証・適用
- 望ましい状態の宣言を `DeclarationRepository` で版管理し、全フィールド（レプリカ数、ダイジェスト、コンテナ仕様（資源上限・マウント・環境変数等）、ネットワーク仕様（公開ポート・外向き規則）、ヘルスチェック仕様）を比較してバージョン間の差分（追加・削除・変更）を決定論的に抽出（`compute_declaration_diff`）。資源やポート、外向き規則、ヘルスチェックのみを変更した場合の個別差分検出をテストで検証（`tests/test_declaration_versioning.sigil`）。
- 適用前にすべてのコンテナ仕様（特権禁止、資源上限必須、digest 固定、ホストマウント禁止）およびネットワーク仕様、レプリカ上限を厳格検証。
- 同一 `commit_id` の重複コミット適用試行、および初回コミットにおける非空 `parent_commit_id` の指定を即座に拒否し、リポジトリの状態（コミット履歴および HEAD）を一切更新しない（一部だけ適用しない原子性を確認）。

### (3) バックアップと復元後の収束
- 整合した時点の状態ストアからエントリを取り出し、長さ前置方式による決定論的 SHA-256 チェックサムを付与したマニフェストを持つ `BackupArchive` を生成（`container/backup.sigil`）。
- チェックサムは偶発的なデータ破損の検出を目的とし、未知バージョンや破損アーカイブに対する復元を即座に拒否。
- 原子的復元において、ストア置換前に各エントリのキー形式（`workload:`, `policy:`, `restart:`, `op:`）、重複キー、件数上限、および行データの復号妥当性を厳格に検査。破損アーカイブでの復元失敗時にターゲットストアが完全に維持される原子性を検証（`tests/test_backup_restore.sigil`）。
- 復元された正常な状態ストアから調整ループ（`reconcile_tick`）を実行し、実行環境（`ModelRuntime`）上で必要なコンテナインスタンスの作成・起動が行われ、宣言された目標レプリカ数と健全性へと確実に収束することを検証。

### (4) 評価器（SIR）とネイティブ（sigil build）の一致
- `test.sh` を通じ、SIR 評価器（`sigil run`）およびネイティブバイナリ（`sigil build`）の双方で同一のテストスイート（全 11 スイート: spec, bundle, tar_fuzz, state, rootfs, runtime, reconciler, network, declaration_versioning, backup_restore, admin_api）を実行し、同一の操作列・戻り値（0 = 全合格）・エラー動作が得られることを確認。

### (5) 特権・環境依存テストの扱い
- 実 OCI ランタイム（runc / crun）や cgroup v2、user namespace を要する結合試験（`test_runtime_e2e.sh`）は、実行環境にランタイムが存在しない場合に黙って成功とせず、スキップされた旨を明示的に出力して記録する。
